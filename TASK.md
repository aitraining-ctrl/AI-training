# Задание: генерация UI-автотестов

Цель: вместе с ИИ-агентом превратить мануальный тест-кейс в UI-автотесты в стиле этого фреймворка, стабильные и без false positive. Полный текст задания и критерии приёмки выдаются вместе со стендом. Здесь описано, что есть в репозитории и куда класть результат.

Оценивается **ваша работа с агентом** (как вы собрали контекст, что проверили, что исправили), а не только зелёный прогон. На вашем стенде могут быть внедрённые ошибки: если тест падает из-за реального бага приложения, это допустимый результат. Опишите баг в `solution/verify.md`.

## С чего начать

1. Выполните «Getting Started» из [README](README.md): `npm install`, `.env` со значениями вашего стенда, `npx playwright test --project=setup`.
2. Создайте рабочую ветку от этой: `git checkout -b solution/<ваше-имя>`.
3. Выберите **один** кейс из [test-cases/storefront.md](test-cases/storefront.md).

## Что есть в репозитории

| Что | Где | Зачем вам |
|-----|-----|-----------|
| Мануальные кейсы | `test-cases/storefront.md` | Вход задания: кейс и связанные проверки регрессии |
| Эталонные тесты | `tests/store/catalog.spec.ts` (витрина, гость, UI + API), `tests/auth/login.spec.ts` (позитивный + негативный), `tests/admin/admin.spec.ts` | Образец стиля: именование, фикстуры, ассерты |
| Page Objects витрины | `pages/store/store.page.ts`, `pages/store/product.page.ts` | Есть каталог и карточка товара. **Корзины и checkout нет:** их Page Objects вы создаёте сами по образцу |
| API-клиент | `helpers/api/admin-api.ts`, фикстура `adminApi` | Проверки и подготовка данных через Admin API вместо UI. Методов мало, добавляйте нужные |
| Фикстуры | `fixtures/index.ts` | Новые Page Objects регистрируйте здесь, тесты импортируют `test`/`expect` только отсюда |
| Правила архитектуры | [README → Architecture Rules](README.md#-architecture-rules) | Частично проверяются `npm run lint` |

## Этапы и результат

| # | Этап | Результат | Куда |
|---|------|-----------|------|
| 1 | **Research.** Кейс, его страница, реальные локаторы (`data-testid`), существующий Page Object, 1 эталонный тест для стиля, валидные и невалидные тестовые данные | Контекстный пакет для агента | в работе с агентом; ключевое кратко в `solution/plan.md` |
| 2 | **Plan.** Шаги автоматизации с проверкой на каждом шаге, граничные и негативные случаи, пометка UI / API у каждой проверки | План | `solution/plan.md` |
| 3 | **Implement.** Позитивный автотест, граничный/негативный (или data-driven) автотест, недостающие Page Objects | Код | `tests/store/` или `tests/checkout/`, `pages/store/`, `pages/checkout/` |
| 3 | Дополнительные ассерты сверх кейса, у каждого причина | Список | `solution/extra-assertions.md` |
| 4 | **Verify.** Оба теста запущены против стенда минимум 2 раза подряд, чек-лист, все правки сгенерированного кода | Прогоны, чек-лист, таблица правок | `solution/verify.md` |
| — | Рефлексия: 5–10 строк, хотя бы одна конкретная правка промпта | Текст | `solution/reflection.md` |

Шаблоны файлов уже лежат в `solution/`, заполните их.

## Полезные команды

```powershell
# Два прогона подряд (проверка на флак)
npx playwright test tests/store --repeat-each=2

# Проверка, что негативный тест действительно ловит ошибку: временно испортите данные или ожидание
# и убедитесь, что тест падает. Верните как было.

# Посмотреть страницу вашего стенда и подобрать локаторы (сессия из setup, ссылку вводить не нужно)
npx playwright codegen --load-storage=playwright/.auth/session.json <хост стенда>/dk/store
```

Если агент исследует страницу через Playwright MCP, запускайте MCP с `--isolated --storage-state=playwright/.auth/session.json`: тогда он видит ваш стенд без 403.

> Ссылка сессии, пароль админа и содержимое `playwright/.auth/` — секреты. Не вставляйте их в чат с ИИ и не коммитьте.
